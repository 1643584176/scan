1. **披露的报告全部是历史漏洞**——它们已被修复或已过时，**不代表目标当前仍存在该问题**。禁止把"某目标某类型漏洞"当作"现在还能打"。

## 3. 推理路径提炼（核心）

> 每条 = 发现者当时的思维过程还原：**业务场景 → 怀疑点 → 为什么这里会错 → 验证方式**。
> 学习目标是这个推理方式，案例本身已过时。

### 3.1 "认证链上少一环校验"型

- **nextcloud ID4me 认证绕过（$2.5k）**：发现者思路——登录链由多个服务协作完成时，每个环节的信任假设是什么？怀疑"JWT 到了但没验签"。**推理方式**：多服务协作的认证链上，找"信任了上一步输出却没验证上一步产出物"的环节。
- **rocket_chat SAML XML 签名包装**：同样的信任链推理——SAML 响应里塞入多个断言，服务端只验证了第一个。
- **rocket_chat 完整认证绕过到 admin**：怀疑"认证网关与业务服务对会话的理解不一致"——网关认为已验证，业务服务认为已授权。

**可迁移的提问**：我的目标里，有没有"多个服务/多个入口协作完成一次认证"的链？链上每个环节是否都验证了上游的产出物（签名/JWT/会话）？

### 3.2 "批量/别名操作放大单次缺陷"型

- **GraphQL Mutation Aliasing DoS（$12.5k）**：发现者思路——GraphQL 允许同一 mutation 用不同别名在一请求内重复执行，服务端是否对"单请求内重复操作"做限流？**推理方式**：协议特性（别名/批量/嵌套）是业务层限流看不见的放大面。
- **PlayStation double fdrop / 嵌套 JAR**：底层资源释放与嵌套解压的放大。

**可迁移的提问**：我的目标有没有"单请求可重复/批量触发同一操作"的协议面（GraphQL 别名、批量接口、数组参数）？这个面绕过了哪些按请求计数的限制？

### 3.3 "查询/过滤参数被当作代码执行"型

- **Elasticsearch Painless script via Query.search（$7k）**：发现者思路——搜索接口的 sort/filter 参数如果直接拼进后端查询语言，用户输入就变成了代码。**推理方式**：搜索/排序/过滤类参数是"用户输入 → 后端查询语言"的桥，桥上没有白名单就有注入。
- **mozilla GraphQL filter 参数 RCE（$12k）**：同样的桥，但发生在 GraphQL 的 filter 参数上，且未认证。

**可迁移的提问**：我的目标里哪些参数会进入后端"查询语言"（SQL/ES 脚本/模板引擎）？这些参数是否有明确的类型/枚举白名单？

### 3.4 "ID 可预测 + 认证边界模糊"型

- **rocket_chat livechat 认证绕过 + MongoDB ObjectId 预测读所有文件**：发现者思路——两件事叠加：认证边界有缺口（livechat 未真正验证身份）+ ID 空间可枚举（ObjectId 可预测）。**推理方式**：ID 可预测本身不是漏洞，但它是放大器——任何认证缺口都会因为 ID 可枚举而变成全量数据泄露。

**可迁移的提问**：我的目标里有没有"可预测 ID + 弱认证面"的组合（文件 key、线程 id、订单 id）？

### 3.5 "校验正则/白名单存在盲区"型

- **khanacademy 1-Click ATO**：域名校验用了正则，正则存在盲区（可绕过），配合开放重定向变成 ATO。**推理方式**：凡是用正则/前缀匹配/字符串包含做安全判断的地方，问"这个判断的输入边界在哪"——输入来自 URL/域名时，正则的边界天然不可靠。

**可迁移的提问**：我的目标里哪些安全判断是"字符串匹配"而非"解析后再判断"（URL 域名校验、回调白名单、路径前缀）？

### 3.6 "跨租户/跨组织的资源边界"型

- **stripo 跨租户数据访问 via AI Hub Campaign**：AI 功能是新建的子系统，租户隔离是后补的，漏洞出在"AI 处理链路上哪个环节没带租户上下文"。**推理方式**：新功能子系统（AI/MCP/集成）的租户边界往往是复制粘贴的，怀疑"引用外部资源（文件/库/模型）时不带归属校验"。

**可迁移的提问**：我的目标里哪些功能引用了"别的租户的资源"（公开文件引用的库、AI 线程引用的文件、MCP 引用的 connector）？引用时校验的是"资源本身可读"还是"资源属于我"？

### 3.7 "GitHub/供应链自动化"型

- **duckduckgo pull_request_target RCE + PAT 泄露**：`pull_request_target` 让 PR 代码在带 secrets 的环境中运行。**推理方式**：任何自动化 CI 上，"输入来自不可信方 + 环境含敏感变量"的组合就是 RCE 温床。

## 4. 把推理方式用到我们的项目（提问清单）

拿到一个新目标，用这些提问产生怀疑（**不是去测检查点，而是先问业务**）：

1. **认证链**：登录/会话由几个环节协作？哪个环节信任了上游输出却没验证产出物？
2. **放大面**：哪些协议面允许单请求重复/批量触发（GraphQL 别名、数组参数、批量接口）？绕过了什么计数？
3. **查询桥**：哪些参数会拼进后端查询语言（SQL/脚本/模板）？有没有类型白名单？
4. **ID 空间**：哪些 ID 可预测（短 ID/自增/时间戳）？哪些认证面是弱的（匿名可触达）？两者是否可组合？
5. **字符串判断**：安全判断是否用正则/前缀/包含而非解析？（域名校验、回调白名单）
6. **租户边界**：引用他人资源的功能（库/线程/文件/connector）校验的是"可读"还是"归属"？
7. **新子系统**：AI/MCP/集成类新功能，是否每个环节都携带租户上下文？
