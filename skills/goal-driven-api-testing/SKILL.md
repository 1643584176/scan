# 目标驱动接口测试（Goal-Driven API Testing）

## 强制学习清单（用户 2026-08 教导，必须执行，详见 经验/全局经验/经验学习13.md）

审查任何接口、构造任何请求、解读任何响应时，以下 12 条为**默认神经回路**，不是可选项：

1. 每个网站都有漏洞，只是没发现（连续失败 = 角度没到位，不是网站安全）
2. 注入三元组（注入什么→到哪→导致什么）才算真正漏洞，写不出三元组的都是小儿科
3. 不做没有参考意义的东西（禁枚举接口/ID/无来源探测；动作必须同时有确定性来源+目标结果）
4. 403 是指纹不是终点（判断构成三问 + 逐项消除法）
5. 200 不等于无问题（未消费入参/未测状态组合/未试表示形式）
6. “参数恰好传对”是盲区（逐参数变形看同一判断是否一致执行）
7. 越权越没有问题（洞在判断不一致处，不在判断缺失处）
8. 身份从 cookie 来，别把对面当傻子（测 URL 即凭证资源/新子系统归属模型/cookie 业务字段）
9. 漏洞集中在处理逻辑层（接口绕过/返参/入参/header/函数问题概率极高）
10. 页面判断→参数→接口映射（JS 条件分支是参数契约确定性来源）
11. 竞争视角（前置黑客会不会也这么想；独特角度才值钱）
12. 温故而知新，测后必复盘（提炼推理路径，不是记录流水账）

## 核心思维框架

**漏洞挖掘的起点是业务，不是接口。**

- ❌ 错误模式：拿到接口清单 → 逐个调用 → 看返回什么 → 分析响应 → "权限正确"→ 停止（这是测接口，不是挖漏洞）
- ✅ 正确模式：理解业务 → 推理漏洞点 → 用接口验证漏洞点 → 让系统返回目标数据

**接口只是验证漏洞点的工具，不是工作对象。** 一个测试动作若没有"验证某个漏洞点是否存在"的业务目的，就没有执行价值。

### 业务漏洞点发现流程（先业务后接口）

1. **理解业务**：画出目标平台的业务模型——核心业务对象（文件/团队/组织/库/席位/订单）、对象间的归属关系（谁拥有谁）、权限层级（匿名→查看→编辑→管理→admin）、业务状态转换（分享/转让/升级/移除成员）。
2. **推理漏洞点**：基于业务语义找出"权限判断可能遗漏"的位置——不是问"这个接口有没有问题"，而是问"这段业务里，谁可能做了不该做的事还被放行"。漏洞点天然存在于：跨对象引用（A 的文件引用 B 的库/计划/线程）、状态转换边界（撤销分享后旧链接、移除成员后旧邀请、降级后旧权限）、批量/聚合操作（一次操作遍历多个对象只校验了第一个）、继承关系（子资源继承父权限时漏检）。
3. **用接口验证漏洞点**：针对推理出的漏洞点，从 JS/抓包/文档中找到消费该业务数据的接口与参数（确定性来源），构造最小请求验证漏洞点是否真实存在。**接口调用到此为止，只服务于漏洞点验证**。

**反例（本 skill 禁止的模式）**：拿到 81 个 view/216 个接口清单后逐个订阅/调用看响应，用"响应是否变化"判断安全——这是给项目测接口，产出对报告毫无价值。

### 目标驱动

接口测试的起点是**目标**，不是接口行为。

- ❌ 错误模式：请求接口 → 看返回什么 → 分析响应 → "权限正确"→ 停止
- ✅ 正确模式：定义"我想要的结果" → 反向设计请求组合 → 让系统按我的要求返回目标数据

接口返回 200、401、403、空数据、无差异，都只是**信号**，不是结论。

**身份定位：漏洞创造者，不是审查者。**
- 审查者：验证接口有没有洞，测完没有就"权限正确"收工
- 创造者：第一次越权/绕过失败后不放弃，盘点所有客户端可控入参（auth 消息字段、viewHash、preload、cookie、ID 字段、模型隐形字段），用知识组合构造把漏洞创造出来
- 服务端在哪里做身份/权限决策，就在哪里伪造入参（信任轴）

## 第一原则

0. **每个网站都有漏洞（信念基础）**：H1 上每个大目标都有已披露的真实漏洞——没有任何网站是无洞的；已披露的只是冰山一角，水面下还有更多。连续失败时想到这一点：没发现 = 角度没到位，不是网站安全。分析 H1 漏洞报告的根本目的就是建立这个信念（漏洞一定存在，只是我们没发现）。
1. **否定性结果 ≠ 安全**：匿名/登录响应一致、均被 401/403 拒绝、返回空对象——都不代表无漏洞，只说明当前请求组合未触及漏洞面。
2. **肯定性结果 ≠ 安全**：HTTP 200 正常返回不代表接口没问题，200 只是服务端按预期处理了该请求，漏洞利用链可能藏在参数构造里。
3. **所有接口都有突破方法**：不存在攻不破的接口。没找到只是方法/角度问题。发现不了漏洞是测试者能力问题，不是系统安全。

**权限的本质是代码里的判断，漏洞就是判断的遗漏：**
- 接口级遗漏：某接口忘了加权限判断（应该校验身份/权限但没有）→ 匿名/低权限直访
- 对象级遗漏：修改数据时忘了判断"数据是不是自己的"（只验登录不验归属）→ IDOR
- 批量遗漏：循环处理多个对象时只校验一次或漏掉逐项校验 → 批量 IDOR
- 找法：对每个修改类操作问"这里判断数据是我的了吗"；对批量接口问"循环里逐项校验了吗"；对同族接口对比"哪些有校验哪些没有"

## 漏洞专家接口审视（看到接口的第一反应）

以漏洞专家身份看待每个接口，按固定顺序触发假设：

1. **这个接口存在漏洞吗？** —— 对每个新接口/参数立即问，不等待响应
2. **以什么方式达到漏洞？** —— 基于接口功能快速建立漏洞假设：
   - 代理/转发类（proxy、figment-proxy、file_proxy）→ SSRF、任意 URL 访问
   - 分页/排序/游标参数 → SQL/查询注入、类型混淆
   - ID 类参数（file_key/teamId/userId/orgId）→ 越权、IDOR
   - 批量类（batch）→ 批量越权、权限校验绕过
   - 信任链输入（preload/header/cookie/hash）→ 身份混淆、参数篡改
   - AI/生成类（cortex）→ Prompt 注入、SSRF、越权生成
   - 代理/OAuth/回调类 → CSRF、open redirect、令牌泄露
3. **构造达到漏洞的请求** → 用目标驱动流程反向设计

接口返回什么只是验证假设的手段：假设先行，构造跟进，结果验证。

**前端校验是后端的恐惧清单（攻击面线索）：**
- 页面上每个前端校验（邮箱格式/必填/长度/URL 格式/数字格式）都在泄露后端担心的攻击面——开发者只为"真正会出问题"的字段写校验
- 前端校验可绕过：直接构造请求绕开前端，直测后端是否真的校验、校验在哪一层
- 转化规则：邮箱格式校验→后端可能拼接/回显邮箱（SQL/XSS）；URL 格式校验→后端可能拉取 URL（SSRF）；必填校验→后端对空值/缺字段处理不当；长度校验→后端截断/溢出
- 校验越严格的前端字段，越可能是后端敏感处理点

**JS 代码里的判断也是接口恐惧的一部分（细节地图）：**
- 下载并分析目标 JS，前端判断揭示后端恐惧的完整细节：权限分支（canEdit/isOwner/role/admin）、接口调用条件（什么权限调什么接口）、字段模型（完整字段清单=隐形字段来源）、错误分支（403/401 处理）
- 前端判断 = 后端可能的信任假设：前端只对 owner 显示删除按钮，不代表后端校验了 owner——前端隐藏入口可能是后端唯一防线
- 分析产出：每个权限分支 → 对应的后端接口/参数 → 构造绕过前端判断的直连请求

**页面判断 → 参数 → 接口 映射提取（接口参数契约的确定性来源）：**
- JS 里每个接口调用周围都有条件分支：什么时候调、带什么参数、什么条件下才带某参数——这些**条件参数**就是后端真实参数契约，直接抓包看不到（未触发条件）
- 提取方法：对每个接口调用点，向上追溯调用链（函数入参/状态变量/权限标志），列出“判断→附加参数”映射，例如：`isOwner → 带 ownerToken`、`teamLibrary → 加 teamId header`、`aiEnabled → 带 aiSession`、`isAdmin → 加 role 字段`
- 这些映射就是**隐形参数清单**：条件成立时才存在的参数，是后端判断的输入；逐一变形（删/换值/篡改）重试，看后端判断是否依赖它
- 页面判断本身可绕过：前端不满足条件就不调用接口，但后端可能不校验该条件——直连接口不带条件参数，若仍正常处理，说明该判断只存在于前端
- 双重用途：① 参数契约来源（确定性，非猜测）；② 前后端判断一致性对比（前端判断存在但后端未校验 = 绕过点）

## 目标驱动流程

### 第 1 步：定义目标结果（WHAT）

明确写出"我想让系统返回什么"：
- 让匿名连接获取私有文件/私有团队数据
- 让低权限用户执行高权限操作（删除、移动、改权限）
- 让系统返回指定用户的个人信息、指定团队的文件列表
- 让系统把我指定的对象当作目标对象处理（身份混淆）

目标必须是**可验证的具体数据**，不是"看看这个接口能不能越权"。

### 第 2 步：反向构造请求组合（HOW）

从目标倒推：哪些请求参数/路径/通道组合能让服务端把目标数据返回给我？按以下维度逐一变换：

| 变换维度 | 具体手法 |
|---|---|
| 标识符表示形式 | 短 key ↔ 数字 ID ↔ 分支 key ↔ URL 编码 ↔ 大小写 ↔ 嵌套对象 |
| 入口通道 | HTTP REST / WebSocket subscribe / WS URL preload / 不同域名 / 不同路径 |
| 查询视图 | 同一资源换其他视图查询（OpenEditorFileData → FileCanUseDevModeDemoFile 等） |
| 客户端类型 | web / desktop / ios / android（不同客户端权限模型可能不同） |
| 参数格式 | JSON 嵌套、附加身份字段（userId/anonymousUserId）、批量数组 |
| 信任链环节 | 服务端信任的每个输入点：preload、header、cookie、签名参数、hash |

### 第 3 步：每轮测试都验证“目标是否达成”（CHECK）

- 目标达成 → 验证利用链完整性（能否稳定复现、影响是否真实）
- 目标未达成 → 回到第 2 步换变换维度，**绝不**因“响应正常/被拒”而停止
- 每个被拒响应都问一句：**“还有什么方式能让它获取到？”**

### 第 4 步：温故而知新，测后必复盘（REVIEW）

- **测完不是结束，复盘才是学习**：每轮测试后提炼——这次为什么想到这个测试点（什么证据/思路引导的）？结果证明了什么？哪个推理错了？下次遇到类似场景第一反应该是什么？
- 提炼的是**可迁移的推理路径**（业务场景→怀疑点→验证方式），不是记录“测了什么/得到什么响应”——后者是流水账，前者才是知识
- 定期温故：回看 H1 报告分析（_h1_toolkit/ANALYSIS.md）、历史测试复盘、经验库——**每次温习都要产生新的怀疑点**，温故而知新，不重复读旧结论
- 新提炼的思路即时沉淀：更新对应 skill/经验记忆/工具包分析文档，让下次会话自动调用，不让用户重复指导

## 被拒后的路径变换清单

当请求被拒绝（403/401/空数据/无差异）时，按序尝试：

1. 换标识符表示：file_key → file_id 数字 → branch_file_key → 编码变体
2. 换接口：主接口被拒试版本历史/元数据/缩略图/实时通道等附属接口
3. 换通道：HTTP 被拒试 WebSocket 订阅；subscribe 消息被拒试 URL preload 参数
4. 换视图：同一资源找其他查询视图（从真实流量/JS 里枚举视图名）
5. 换客户端：clientType 变换（desktop/ios）
6. 换参数组合：附加身份字段、批量形式、嵌套表示
7. 换信任链输入点：URL 参数中服务端直接消费的 ID（如 preload 里的 teamId）

## 参数敏感思维（遇到特定参数立即触发注入怀疑）

识别参数类型并立即检查注入面，不要等接口报错才想到：

| 参数类型 | 敏感点 | 测试方法 |
|---|---|---|
| 分页数值（page_size/page/firstPageSize/count/limit/offset） | SQL LIMIT/OFFSET 拼接、数值类型校验 | 负数、零、超大数、字符串（"1 OR 1=1"）、浮点、数组、对象、布尔 → 观察异常/回显 |
| 排序参数（sortOrder/order_by/sort） | ORDER BY 直接拼接（经典 SQL 注入位） | 枚举外的任意字符串、SQL 语法（`DESC;--`、`name DESC`）→ 观察是否拼接生效 |
| 游标参数（before/after/cursor/next_token） | 游标解码后用于查询定位（SQL/NoSQL 注入、身份混淆） | 解码游标看结构、篡改游标内部字段、非法 base64 |
| 任意数值参数 | 类型混淆绕过校验 | 字符串、数组、对象、超大数替换数值 → 观察行为差异 |
| 枚举参数 | 枚举之外的值是否被接受/忽略 | 传任意字符串 → 若被接受或报错，说明服务端可能直接拼接 |

检查要点：
- 错误回显：异常输入是否泄露查询结构（SQL 片段、堆栈、字段名）
- 行为差异：异常输入是否产生与正常输入不同的业务状态（不只是 500）
- 拼接痕迹：响应里是否回显了拼接后的查询条件

遇到分页/排序/游标接口的第一反应必须是"这里会拼 SQL 吗"，这是最常被忽略的注入位。

## 隐形字段与 Mass Assignment（响应字段 ≠ 可写字段）

UI/接口只暴露部分字段（如只显示改 age）不代表接口只接受这些字段。服务端 ORM 批量赋值可能接受**资源模型的全部字段**，即使响应不回显，数据库可能已经悄悄变了。

**测试方法：**
1. 用确定性来源拿完整字段清单：GET 响应字段、JS 数据模型、服务端文档（禁止猜测字段名）
2. 找出未暴露的敏感字段：id、role、admin、status、owner_id、orgId、workspaceId、验证状态（email_validated_at/student_validated_at）等
3. 在写请求中提交隐形字段（附加到正常字段旁）
4. 响应 200 不算完：**必须用读接口二次验证数据库是否变化**（再 GET 一次对比字段值）

判断标准：业务状态是否真实变化（数据被改、权限提升、归属变更），不是响应码或回显。

## 五步信任链分析与表示变换（经验1：接口绕过核心）

同一个业务动作有无数种协议表示，后端只拦截了其中一种就认为安全。绕过本质是换一种表示提交同样的语义，看校验是否被一致执行。

**五步推理模板：**
1. 画正常请求的信任链：鉴权方式（Cookie/Bearer）、Content-Type、来源校验（Origin/Referer）、CSRF-Token、CORS 预检——判断每一环是强校验还是顺带
2. 列出被隐式信任的假设：如"JSON 接口只会收 application/json"、"复杂请求会触发预检所以跨站不可能"、"Cookie 鉴权不需要 CSRF 防护"、"内部代理只服务内部系统"
3. 对每个假设做表示变换试探：换 text/plain、form、multipart、XML；enctype=text/plain 把复杂请求变简单请求绕开 OPTIONS 预检；JSON 末尾追加 = 测解析器宽容性；Origin: null、空 Referer 测来源校验
4. 逐条证伪：必要条件全部满足才算漏洞（Cookie 能跨站携带、后端容忍解析差异、无额外头鉴权、目标为写操作）
5. 判定：只报 200 不算，必须验证业务状态真实变更（Mutation 生效、数据被改、请求被转发）

**四个可迁移的绕过轴：**
- 入口轴：同一资源的多条等价路径（REST/GraphQL/批量/导出/搜索/异步任务/Webhook），可能只保护了其中一条
- 表示轴：Content-Type、编码、参数位置（query/body/header）、大小写、重复参数（HPP）
- 解析器轴：Nginx 到框架到应用对同一输入理解不一致（parser confusion），把恶意数据送到防护没覆盖的解析层
- 信任轴：谁在最后一步做决策就攻击谁的输入；检查服务端是否信任客户端可覆盖字段（如 current_user、价格、状态、redirect_uri）

使用时机：分析任何接口时先问"这个接口的哪些属性是被后端假设而不是被后端校验的"，再对每个假设做最小变换试探，最后证伪。

## 响应状态即服务端判断指纹（403/200 都是推理起点）

**接口返回什么码不重要，重要的是这个码泄露了服务端什么判断。** 每个状态码都是一段服务端校验逻辑存在的证据，读指纹 → 找盲区。

### 403/401/404 = "这里有一个判断"

- 不要停在"权限有问题"就结束——问：**这个判断由什么构成？缺什么会导致放行？**
- 判断构成三问：① 校验对象是谁（身份？归属？属性？）；② 校验依据来自哪（header？cookie？参数？服务端查库？）；③ 什么输入不经过这个判断（其他入口？其他表示？其他客户端类型？）
- 逐项消除法：每次只撤一个条件重试（撤 header / 换 content-type / 加字段 / 换通道 / 换表示），看哪个条件被撤后放行——放行的那个就是判断盲区
- 403 还可能是"判断存在但输入未到达判断"：参数名不对、格式不对导致校验被跳过（宽松解析器吞掉恶意字段）

### 200 = 只证明"这个请求组合被接受"

- 200 不能证明接口没问题：它只说明当前请求形式通过了，漏洞可能藏在未测试的分支
- 追问：这个接口还有哪些**未消费的入参**（隐形字段/未用参数）？哪些**状态组合**没测（已删对象/已撤销分享/已移除成员后旧引用）？哪些**表示形式**没试（换 content-type/嵌套/数组/重复参数）？
- 200 + 无差异也不代表安全——只代表当前组合未触及漏洞面

### "参数恰好传对"是测试盲区（看似无漏洞的成因）

- 网站看起来没漏洞，可能只是**你的参数恰好传对了**——用正确参数（自己的 ID/正确格式/完整必填）访问，系统当然正常，这不证明传错也安全
- **"传对了"本身就是证据**：说明服务端在消费这个参数做判断。那么"传错"会怎样？换掉/删除/变形该参数，看判断是否被破坏——宽松处理直接放行，或报错泄露判断结构，都是发现
- 反推法：对每个"看起来正常"的响应，逐个参数问"如果我是服务端，这个参数是不是我判断的依据？"——是的话，改它重试，看同一判断是否被一致执行
- 多参数联合校验：服务端可能用 A+B 联合判断，你只改了 A 保留 B 正确，判断仍通过/仍拒绝——所以每个参数都要单独变形，再两两组合变形
- 注意"参数传对"的不同层：值对（ID 属于自己）、格式对（类型/结构匹配）、表示对（content-type/编码/位置）——三层都要逐个破坏试探

### 基础漏洞已被人挖完，找的是深层判断遗漏

- 表层漏洞（直接 IDOR、简单反射 XSS、明显越权）大概率已被发现修复，重复发现无价值
- **越权是所有人第一个测的东西，所以成熟网站对越权防护最严——“越权越没有问题”**：直接换 ID 读他人数据在正常网站几乎不存在，不要浪费时间验证表层越权
- “越权被防住”不是结论而是证据：证明归属判断存在；判断存在 → 才有分支/盲区/遗漏——真正的洞在**判断的不一致处**（同数据多入口权限不一致、新功能子系统分支没继承校验、状态转换后旧权限残留），不在判断的缺失处
- 找“不易被发现”的：跨对象引用的归属校验缺失、状态转换边界的旧权限残留、批量/聚合只校验首项、子资源继承父权限漏检、表示变换绕过单一校验、多入口权限不一致
- 判断标准不是“有没有漏洞”而是“这段判断有没有遗漏分支”

### 身份从 cookie 来：跨账号越权几乎不可能（别把对面当傻子）

- 后台取身份（当前是谁/属于哪些资源）是从**会话 cookie** 取的，不是从请求参数取的——传谁的 ID 都没用，cookie 里的身份拿去比对目标资源，基础越权（A 访问 B）必然被拒
- **别低估对面网站**：权限问题是所有测试者都知道的核心，对面工程师更知道——基础权限校验（身份→归属→授权）一定存在且严密，不要在“校验是否存在”层面浪费时间
- 这条认知划出真正的测试面：
  - URL 即凭证的资源（预签名 URL/一次性 token/匿名通道/分享链接）——不经过 cookie 身份解析，鉴权依赖 token 本身，token 的生成/可预测性/生命周期才是测试点
  - 新对象/新子系统的归属模型（AI 沙箱、snapshot、派生对象）——校验可能在创建时做了，但对象与源资源的权限关系是新逻辑，问“判断有没有继承”
  - 从 cookie 取值的业务字段（若 cookie 存了 fileKey/teamId/角色等可控字段，篡改它看判断是否被绕过）
- **多账号 cookie 陷阱（header 伪装假阳性）**：header 声明身份（如 X-Figma-User-ID）时，服务端通常从会话 cookie 的 authn 段找该身份对应的 token，找到才放行。浏览器多账号登录时 authn 会同时缓存多个账号的 token——此时用 A 的 header + 同一 cookie 返回 200 只是"该 cookie 恰好含 A 的 token"，不是 header 信任漏洞。判定必做：解析 authn（URL decode→JSON 看含几个 uid）→ 构造只含攻击者自身 token 的纯净 cookie（紧凑 JSON 重新 URL encode 替换）→ 纯净 cookie + 伪装 header 重测，401 = 绑定存在非漏洞；正向对照（纯净 cookie + 匹配 header 应通过认证而非 401）排除格式损坏干扰

### 漏洞集中在处理逻辑层，不在权限层（函数问题概率极高）

- 权限判断是“明牌”（人人知道要做，对面防得最严）；漏洞真正集中在**处理逻辑层**——接口绕过、返参、入参/请求体/header 的处理、以及具体函数实现缺陷
- **接口绕过**：前置检查/网关/校验层存在可绕过路径（表示变换、入口变换、路径归一化、大小写/编码变体、中间层缺陷）
- **接口返参**：响应返回了不该返回的字段/对象（聚合响应带他人数据、冗余字段、内部信息、token、错误堆栈）——对每个响应字段问“这个字段为什么出现在这里”
- **入参/请求体/header**：输入被消费的位置——服务端在哪些地方消费了客户端可控输入（不只是业务字段，还有 header、cookie 里的业务值、未文档化字段）
- **函数问题（出漏洞概率极高）**：具体处理函数的实现缺陷，工程师不会为每个函数写防御代码，正常输入表现正常，畸形输入才触发：
  - 解析函数：JSON/URL/QueryString 对重复键、嵌套、畸形、超大值的宽容性（重复键取哪个值？非法 JSON 被吞还是报错？）
  - 编解码函数：双重解码、base64 变体、URL 编码差异、Unicode 归一化
  - 类型转换：宽松比较、字符串转数字截断/溢出、数组 vs 标量
  - 哈希/签名函数：算法混淆（alg=none）、密钥选择错误、长度扩展、时序比较
  - 随机/ID 生成：可预测、时间戳种子、计数器、短 ID
  - 字符串处理：截断、大小写、空字节、换行符
  - 路径/文件处理：拼接、扩展名判断、符号链接、编码差异
  - 状态转换函数：状态机边界、重复转换、回退、撤销后重放
  - 聚合/批量处理：首项校验、去重、排序后处理、分页游标
- 触发方式：畸形输入（“参数恰好传对”的反面）——每个函数缺陷对应一种畸形输入，主动构造去触发

### 注入三元组：真正意义上的漏洞标准

- 真正意义上的漏洞结构是**注入三元组**：注入**什么**（载体）→ 注入到**什么地方**（消费点）→ 导致**什么问题**（后果），其他（权限遗漏/逻辑缺陷/状态码差异）都是小儿科
  - 载体：参数、请求体字段、header、cookie、文件名、URL、模板字段、JSON 键名
  - 消费点：SQL 查询、命令执行、模板引擎、文件路径拼接、HTTP 请求构造（SSRF）、日志、响应头、正则、反序列化
  - 后果：数据泄露/篡改、RCE、SSRF、任意文件读写、响应头注入、日志伪造
- 为什么注入才是真正漏洞：权限/逻辑类是“判断遗漏”——加个 if 就修好、影响单点；注入类是“信任了不该信任的输入”——影响执行层/数据层，修复要重构（参数化/白名单/沙箱），才是高危
- 判定标准：发现必须能写成完整的“注入 X 到 Y 导致 Z”三元组；写不出来的（响应差异/状态码变化/权限被拒）都是小儿科，不值得报告
- **公开性检查（任何测试链的绝对第一动作，提交前必做）**：判断查到的东西是否公开——公开的发现毫无意义（by design/必 dup/对面早知道）。**执行时机：不是提交前，而是测试链启动时**——第 0 步就验证目标对象是否公开（匿名访问对照：私有对象匿名 403 vs 公开对象匿名 200），公开 → 立即终止整条链，零浪费。检查五问：① 该数据是否无需任何凭据即可获取（匿名直连/公开页面/公开 API）？② 目标对象本身是否被 owner 设为公开（公开分享/公开文件）？③ 其他用户/匿名用户是否本就有权查看（有 = 不是漏洞）？④ 数据是否出现在产品页/营销页/文档等设计公开渠道？⑤ 获取路径是否需要特殊知识（deep link/未公开参数）——若公开渠道同样能拿到，特殊路径也不构成泄露。任一为“公开”→ 无意义，不报告。Foundry 链教训：B 对 A 的 Make 文件 sandbox 200 看似分支差异，实际文件本身公开分享（匿名 200 vs 私有文件匿名 403），整条链 by design——公开性检查未前置导致浪费全部核心测试；PlanByFileKey 匿名计费数据被关 Informative 同理
- 测试转化：对每个接口的每个输入点问“**这个输入会注入到哪个消费点？**”——从 JS 逆向找消费点（参数进了哪个函数：查询构造/URL 拼接/路径拼接/命令拼接/模板渲染），再构造畸形输入注入
- 与函数问题的关系：函数是消费点，注入是攻击方式——找到消费函数 → 推断拼接方式 → 注入载荷

### 回显语义与时间特征：EMPTY 的两种语义（回显型漏洞判定工具）

回显型接口（服务端 fetch 回显/文件读取回显/代理回显）返回“空”时，**必须先区分两种语义再下结论**，否则结论可能翻转：

- **语义 A：连接成功但响应被丢弃** —— 服务端拿到了响应，但非 200/非预期格式不落盘不回显
- **语义 B：连接失败** —— 目标根本不可达

**判定方法（对照实验）**：
1. **回显语义验证（先做）**：测目标服务自身返回 401/403/500 的 URL（如 httpbin.org/status/401）——若同样空，说明**只回显 200 响应** → 所有“空”都可能是语义 A → 影响面收窄为“200 才回显”（SSRF 只能看到 200 页面，非 200 静默丢弃）
2. **时间特征**：快速返回（<1s，与正常 401 对照组耗时一致）= 连接成功（语义 A）；慢返回（超时特征 1.5s+）= 真连接失败（语义 B）——用延迟区分“成功但被丢弃”与“失败”
3. **路径存在性**：读回时检查目标路径是否出现在结果流（path_absent vs path_exists）——文件没写进去 = 未落盘

**实战案例（Figma foundry SSRF 深化，2026-08）**：内网/IPv6/编码变体全部“空”，但 sboxd 内部域名 0.9s 快速返回（与 httpbin 401 的 0.8s 一致）→ 判定连接成功返回 401 被丢弃（公网行为，无内网证据）；IPv6 2.2s 慢返回 → 真隔离。结论：网络层隔离完整覆盖 IPv4/IPv6/编码/DNS 变体，SSRF 只回显 200，评级 Low-Medium 维持，升级无门。第一轮差点误判内部域名组——不先做非 200 对照，EMPTY 的两种语义无法区分。

### 竞争视角：站在前置黑客的角度审查接口

- **你不是唯一在找漏洞的**：大目标（Figma/Shopify 等）有大量赏金猎人在挖，还有自动化扫描器全天跑；你想到的思路别人大概率也想到过，甚至已提交并被修复
- **自检过滤器**：每个测试想法先问“这是不是任何黑客都会测的？”——自然的思路（换 ID、改参数、常见绕过姿势）别人早试过，洞早被补，测了白测且提交必 dup
- 先自我审查“前置黑客会不会也这么想”，再评估“他们为什么没想到”——独特角度的来源：别人只看网络请求你读了 JS 源码、别人只测主链路你测了异常状态转换、别人单测一个子系统你组合了跨子系统链、新功能初期防护不完整、非标准表示（伪造 content-type/数组/重复参数）
- 时间价值：别人已经测试过的区域会留下痕迹（H1 hacktivity 已披露的同类漏洞类型 = 已被覆盖区域，避开）；你的竞争力在独特场景理解 + 深度逆向 + 跨子系统组合
- 报告竞争力：大目标重复报告多，报告必须有前置黑客没提过的新角度才不会被 dup

### 请求构造不受项目约束

- 项目里的请求只是开发者实现的一种表示，不代表服务端接受的全部表示
- 同一个业务动作可伪造：Content-Type（json/text/plain/form/multipart/XML）、参数位置（query/body/header/cookie）、大小写、重复参数（HPP）、编码变体、附加字段、数组/嵌套
- 即使一个接口，也要问"换一种表示，同一个校验是否被一致执行"

## 反模式黑名单（每次测试前对照检查）

0. **不做没有参考意义的东西**：禁止枚举接口（拿清单逐个打）、禁止枚举 ID（猜值/遍历）、禁止无确定性来源的探测——每个测试动作必须同时满足：① 确定性来源（JS 调用定义/真实抓包/已有日志证据，不猜参数不猜 ID）；② 预定义目标结果（能写成注入三元组或业务状态变更）；缺任一即不做，立即切换方向。
1. **禁止端点矩阵枚举式测试**：把全部端点批量打一遍看谁返回 200/403/404，是“测项目”式验证，产出对报告毫无价值（Notion 61+ 端点矩阵全关即此教训）。只挑**有业务语义**的接口（写操作、权限变更、数据返回、认证流程），每个预定义利用目标后针对性构造请求。
2. **每个测试执行前必须书面定义目标结果**——期望服务端执行的越权动作或返回的敏感数据；定义不出目标结果的测试不做。
3. **状态码/错误信息变化不是发现**：只有业务状态变更（越权动作成功/敏感数据返回）才算结果；200/403/404/空都不是结果。
4. **连续否定立即切换攻击面**：连续 403/404/空意味着当前方向错误，切换到另一个信任链/攻击面，禁止通过扩大端点清单继续验证同一方向。
5. **任一接口都可能存在突破口**：任何接口（哪怕只读、哪怕看似无害）都有利用可能，逐个接口针对性地找绕过（表示变换/身份混淆/参数组合），而不是验证一遍"权限正确"就放弃。

## 注意事项

- 所有参数必须来自**确定性来源**：JS 调用定义、真实抓包、服务端文档。**严禁猜接口入参、严禁枚举入参/ID 值**（猜参数名、枚举 fileKey/userId 都是无意义动作）。变换的是已有入参的表示形式（换值/换格式/换位置），不是凭空造参数。
- 只做能服务目标结果的测试；纯行为测绘、确认参数是否被忽略的验证不做。
- 判断标准是**目标数据是否到手/业务状态是否变化**，不是 HTTP 状态码或错误类型。
- 测试以绕过（认证/校验逻辑）为唯一目的。
- 发现"无越权痕迹"时，把结论写成"当前方法未触及漏洞面"，而不是"不存在漏洞"。
