# 经验学习12:SSRF 任意 URL 注入载体选择与校验链逆向

## 适用场景
- 发现服务端 fetch 任意 URL 并解析内容(JSON/配置)的 SSRF 端点时
- 需要把攻击者可控内容"喂"给服务端(JSON 注入 / profile 注入 / 配置覆盖)时
- 需要证明 SSRF 数据读取深度(盲打 → 内容解析)时

## 核心方法

### 1. 校验链逆向(错误分类即信息泄露通道)
先用已知行为的外部服务逐一探测,把每个错误分类与触发条件精确对应。错误信息本身是最可靠的信息泄露通道,可用于内网测绘:
- **Network error** = DNS 或 TLS 失败 → 域名不存在/不可达(子域枚举的否定信号)
- **Connection timeout** = 主机存在、端口可达但无响应 → 证明内网主机/端口开放
- **Http error** = 目标存在但状态码非 2xx
- **内容读取** = 返回 "Invalid content type"(2xx 非目标类型)→ 证明响应体被服务端完整 fetch
- **JSON 解析** = 返回缺字段错误(如 "Missing xxx version")→ 证明响应体被完整解析 = 数据读取级证据

### 2. 校验规则精确化用"已知行为服务",不在未知服务上猜
- 例: jsonplaceholder 无 Cache-Control 头也能过校验 → 反推规则是"必须有 cc 头且不含 no-cache/private",而非"必须是 public"
- postman-echo /response-headers 响应头完全可控(body 固定回显)→ 适合分离"头部校验"与"内容校验"两个维度

### 3. 载体三条件(用于注入攻击)
内容可控 + content-type 匹配 + 缓存头有效 + 公开 GET 200 且无重定向(重定向不跟随的 SSRF 要求直接 200)

### 4. 最佳载体方向:目标自身的 CDN/公开存储
- 按文件扩展名返回 content-type(上传 filename=evil.json 的合法文件 → CDN 返回 ct=application/json)
- 缓存头通常 public(404 页也会带 cc=public, max-age=N)
- 上传通道优先找: 商品图片、头像、附件、文件导入(注意可能触发人机验证)

### 5. 托管服务实测表(2026-08 快照)
| 服务 | 结论 |
|---|---|
| postman-echo /response-headers | 头完全可控,body 固定回显 |
| webhook.site | 响应头固定 no-cache, private;actions 全需付费订阅 |
| jsonplaceholder | cc=max-age=43200 可过校验,内容不可控 |
| uguu.se | 无 cc 头被拒 |
| 0x0.st | 上传功能关闭(503) |
| paste.rs | 固定 ct=text/plain |
| jsonblob / jsonkeeper | 403 / 404 |
| mocky | 证书问题 |

### 6. 目标自身预签名 URL 一般不可作载体
- 云存储预签名 URL 通常只覆盖 PUT 方法(GET 403)
- acl 被签名强制私有,请求头改不了
- 签名只覆盖 host 与 method → bare PUT(仅 User-Agent)可成功;拼参数/加头破坏签名(403/400)

## 注意事项
- 校验链错误分类 → 内网枚举要分开记录"否定信号"(Network error)与"肯定信号"(Http error/Connection timeout/内容读取)
- 重定向不跟随的 SSRF:载体必须直接 200,不能用 301→目标 的跳转服务
- OIDC 探测(/.well-known/openid-configuration)是验证"内网 JSON 可读"的最快路径——几乎所有内部服务都有该端点
