## 一、核心方法论 1:header 伪装假阳性的判定(多账号 cookie 陷阱)

**场景**:用 B cookie + X-Figma-User-ID=A 调用接口返回 200,拿到 A 的数据——初看像"服务端信任 header 身份"的高危漏洞。

**致命陷阱**:浏览器多账号登录时,`__Host-figma.authn` cookie 会**同时缓存多个账号的 token**。服务端校验逻辑是:header 声明 uid → 从 authn cookie 找该 uid 的 token → 找到即认证通过。因此"伪装 A 成功"只是因为你抓的 cookie 里恰好有 A 的 token。

**判定流程(必做)**:
1. 解析 authn cookie(URL decode → JSON),查看含几个 uid
2. 构造纯净 cookie:只保留攻击者自己 uid 的 token(紧凑 JSON 重新 URL encode,替换原 cookie 的 authn 段)
3. 用纯净 cookie + 伪装 header 重测 → 401(绑定存在,非漏洞)/ 200(真漏洞)
4. 反向对照:只留目标 uid token + 自己 uid header → 401
5. 正向对照:纯净 cookie + 匹配 header → 认证通过(400/403 而非 401,证明格式有效)

**结论**:X-Figma-User-ID 必须匹配 authn 中的 token。攻击者只有自己的 token,无法伪装他人。

## 二、核心方法论 2:403 错误消息演化 = 校验分层图

同一端点连续改变传参,403 消息逐层变化,就是服务端校验管线的剖面图:

- 不带 owner header → `"Thread owner ID and thread owner type required"`(第 1 层:参数存在性)
- 带上 X-Figma-Owner-ID/Type → `"AI is not enabled"`(第 2 层:功能可用性)
- 换成 plan 维度 → `"Unauthorized for this plan"`(第 2 层变体:plan 授权)

**用法**:
1. 每一层 403 都是"该校验存在"的证据,不是终点
2. 错误消息的措辞 ≠ 字段名(说 "Thread owner ID required" 不代表字段叫 threadOwnerId——JS 全目录搜 threadOwner 零命中)
3. 判定端点是否可测:**owner 自己(基线)都 403 时 = 端点需要运行时状态,无法独立建立基线,果断收束**,不要继续猜参数

## 三、核心方法论 3:IDOR 的三级确认(不满足于列表 403)

列表接口 403 后,对象级操作必须全测:
1. **直击对象 ID**:GET/PUT/DELETE /threads/{id}(消息、改名、删除)
2. **owner 上下文替换**:用自己有权对象的 owner_id + 目标对象 ID → 若 200 = 线程-owner 绑定缺失
3. **404 vs 403 语义**:404 "Thread not found" = 服务端**按 owner 命名空间查找对象**(隔离在查询层,强绑定);403 = 查到对象但权限拒绝(弱于 404,可能有 IDOR 空间)

本案例:owner 替换 → 404,证明线程按 file 命名空间隔离,IDOR 不成立。

## 四、案例结论:Figma ai_chat threads 权限模型(已收束)

| 层 | 检查 | 结果 |
|---|---|---|
| 认证 | 匿名访问 | 401 |
| 文件级 AI 权限 | B→A 任何文件读/建/改/删 | 403 "no permission to use AI in this file" |
| 线程-owner 绑定 | owner 替换 IDOR | 404 "Thread not found" |
| plan 维度 | owner_type=plan 查他人 plan | 403 "You don't seem to have permission" |
| header 伪装 | 纯净 cookie + 他人 uid | 401 |

owner_type 支持枚举:file/plan(team/user/org 不支持)。B 在自己文件创建线程 200 → 排除 plan 因素,403 确系文件权限。
