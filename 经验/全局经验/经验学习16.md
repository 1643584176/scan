# 经验学习16：MCP Profile 注入边界判定法与托管平台载体优先（2026-08-19）

## 一、场景
Shopify catalog.shopify.com MCP 端点存在 profile 参数注入（恶意 agent profile JSON → 服务端加载）。判断该注入能否形成提权/解锁敏感工具链，以及如何用最低成本找到满足校验条件的注入载体。

## 二、Profile 注入边界判定法（两步裁决，30 分钟内出结论）

**核心模型：工具可见性 = 注入 profile 的 capabilities ∩ 服务端允许集（交集）**

第一步——测认证门槛：
- 用**官方合法 profile**（不是恶意 profile）调用目标高权工具（checkout/order/cart 等）
- 若官方 profile 也 "Tool not found" → 工具被服务端认证门槛挡住，与 profile 无关 → 注入永远无法解锁
- 若官方 profile 可调用 → 说明工具在允许集内，继续第二步

第二步——测白名单扩张：
- 注入带猜测 capability 名（merchant/admin 级）的 profile，每个名字配唯一标记 URL（spec/schema 指向 example.com 子域）
- 观察两类回显通道：
  1. 工具集变化（tools/call 是否出现新工具）
  2. **structuredContent.ucp 回显**（成功响应回显服务端规范化后的 capabilities——注入的名字保留=被接受，消失=被丢弃；URL 被替换成官方值=白名单映射）
- 全部被丢弃 → 白名单强制交集，注入只能收缩（DoS 自己）不能扩张 → 无提权价值

**关键洞察：structuredContent 回显是服务端白名单指纹通道**——不用盲猜白名单，注入一批名字看回显哪些留下即可枚举允许集。

## 三、二次 SSRF 判定（5 分钟）
- 把 profile 的 spec/schema 字段指向第三方可记录请求的服务（webhook.site）
- 触发 MCP 调用后查 webhook 请求记录：有新请求=二次 fetch；无新请求=白名单映射（不 fetch 注入 URL）
- 同时该记录可确认服务端 fetch 的请求头（UA、是否带 Authorization/cookie）→ 凭据窃取可行性判定

## 四、托管平台载体优先原则（替代目标 CDN 方案）
注入载体四条件：内容可控 + ct=application/json + cc 有效(含 public 无 no-cache/private) + 公开 GET。
载体优先级：**用户已有账号的托管平台 > 目标 CDN > 第三方 paste 服务**。
- Vercel 静态部署（hobby 免费）：profile.json → vercel.app 返回 ct=application/json + cc=public ✅ 一次通过全部校验
- 部署方式：`npx vercel deploy --prod --yes --token <vcp_token>`（CLI）；**坑**：v13 REST API 的 files 会进 src/ 子目录导致 404，CLI 才部署到根
- **可达性坑**：deployment URL（带随机段）可能本机/代理不可达，但 alias URL（项目名.vercel.app）可达；服务端（海外）两者都可达——测试时用 alias，验证时用服务端响应时间（~1s=连通）判断

## 五、SSRF 提交门槛复盘
内网 JSON 解析 + 子域枚举 + 2xx 内容读取都是"simple interaction"，过不了 Shopify 官方规则（"simple HTTP/DNS interaction alone is not considered a vulnerability"）。必须有：元数据服务访问 / 内网凭据获取 / 提权链。证据完备≠可提交，规则审查前置省报告机会。

## 六、本案例结论
- Vercel 载体打通 ✅
- 注入边界：交集模型，无法提权 ❌
- 二次 SSRF：不 fetch ❌
- 凭据窃取：服务端 fetch 无凭据头 ❌
- 剩余方向：认证态测试（token 后允许集可能扩大，payment_handlers 注入或有效果）
