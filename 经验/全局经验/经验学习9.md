# 权限绕过穷尽测试复盘：Figma B→A 文件越权（经验学习9）

> 定位：案例 + 执行规范。匿名/低权账号对目标文件全通道被拒时，系统性穷尽"创造权限"路径的完整清单，以及"确认无漏洞"的裁决标准。

## 一、问题现象

目标文件 `5Gs4PaTz11Hlk2sqVnidBG` 是 A 账号的私有文件（Untitled，creatorId=A，linkAccess=plan_edit）。B 账号（无权限）与匿名访问时：
- HTTP API → 403（"You don't have permission to view this file"）
- multiplayer WS → 1005 拒绝
- livegraph WS → 空壳（无 computations）

用户要求："没有权限就创造权限绕过"——不能因被拒就关闭攻击面，要穷尽所有"服务端可能信任的声明"。

## 二、核心认知（先想清楚再动手）

1. **多账号测试第一件事：验证 cookie 与账号的对应关系**。用 `/api/user/state` 逐一确认每个 cookie 文件的 user_id/team_id。本轮曾把 B 的 cookie 误当 A 用了大量测试（ws_cookie_latest.txt 实为 A），导致整个测试矩阵的基线/攻击角色反转、结论全部重做。这是最高代价的教训。
2. **权限被拒 = 服务端不信任你声明的身份**。绕过思路不是"换个拒绝方式"，而是找**服务端真正信任的声明源**（cookie/token/session），再想如何获取或伪造它。
3. **三入口权限模型一致性是裁决前提**：HTTP、multiplayer（1005）、livegraph（空壳）各自独立实现，但权限判定可能共用同一授权层。只有三入口全部确认一致，才能下"无绕过"结论。
4. **空壳 ≠ 无数据，可能是等待时间不足**：livegraph 的 computation 帧（name/canReadV3/libraryKey/signedThumbnailUrl 等）异步延迟 1-15 秒到达。只等第一个 mutations 帧就返回会漏判。每视图独立连接、等满 15s、按 mutations key 配对，才是干净实验。
5. **响应码只是线索，业务数据才是证据**：401/403/1005/空壳都只是"拒绝形态"，判断标准是"是否能拿到目标数据/触发状态变化"。

## 三、绕过穷尽清单（11 类，按"服务端信任什么"组织）

### 1. 身份声明伪造（URL 参数 / 协议帧）
- livegraph URL 的 `userId`/`anonUserId` 参数、auth 帧 args.userId
- multiplayer URL 的 `user-id` 参数
- 结果：全无效。authSuccess 返回 `userId:null` = URL 声明与 cookie 身份不一致（cookie 优先，URL 参数不被信任）

### 2. 角色声明（multiplayer role 参数）
- role=editor/viewer/owner/commenter/admin 全组合 × 匿名/A/B
- 结果：全 1005。注意 **A 对无权限文件声明 viewer 也 1005**——role 参数不信任，权限判定按 cookie 身份

### 3. 会话状态注入（preload / sessionId）
- preload 参数注入：服务端会解析并重新订阅，但只能触发**已存在视图**（view-does-not-exist 报错），权限判定不变
- sessionId：authSuccess 里服务端生成（session-*），不可伪造

### 4. 跨租户参数（teamId/orgId 注入）
- FileBrowserSidebarData(currentTeamId=A团队) 用 B 会话查 → **服务端忽略传入参数，按会话身份返回 B 自己的数据**
- FileBrowserPaginatedRecentFilesView → 服务端从会话取 userId，无法注入他人
- 结论：视图参数是"建议"，根身份永远来自会话

### 5. HTTP 子端点盲区（/api/files/{key}/...）
- videos/audios/page_thumbnails/related_links/reference_id/media_exports/node_status/last_interaction
- 结果：匿名全 401（missing_authentication），A 无权限文件 404（SPA 回退）——无盲区

### 6. 元数据/预览通道（og / embed / community）
- 匿名 file 页 HTML：og:title 只有 "Figma"（无文件信息）
- embed API：400 embed_error
- community API：需登录或与目标文件无关联
- 结果：无盲区

### 7. 库数据面（Library 视图链）
- LibraryFileSubscriptions 匿名泄露公开文件订阅的库文件 key（libraryFileSubscriptionOverridesV2）
- 但库文件本身匿名空壳（权限正确）——**存在性泄露无利用价值**
- LibraryOrgSubscriptions/LibraryTeamSubscriptions（外部企业组织）→ 空壳

### 8. 外部团队/组织深度探测（planPublicInfo 同源）
- TeamByIdForPlanView/OrgByIdForPlanView → **planPublicInfo 放行**（IDOR：匿名查任意 teamId 的 tier/planRecordId/orgId）
- TeamPermissions/TeamCanEdit/TeamByIdForPlanUserView/LibraryOrgSubscriptions → 空壳
- 结论：只有"公开计算器"放行（设计如此），权限相关计算器全部拦截

### 9. 独立权限体系（api.figma.com REST API）
- 匿名/带 web cookie → 403 "Invalid token"（只认 Bearer token）
- **token 通道未测**（需目标账号创建 personal access token）——独立认证体系，权限判定可能与 Web 不同，是唯一遗留通道

### 10. 认证方式变体（reference_id 双向映射等）
- POST /api/files/{key}/reference_id、GET /api/reference_id/{id}/file_key
- 结果：全 401（且 POST 需要完整 header 组合）

### 11. 计算器权限门确认
- 私有文件（B/匿名）无任何 computations = 权限门在计算器层，服务端对无权限文件不计算字段
- 公开文件匿名计算 9 个字段（editorType/name/canReadV3/canViewPrototypeV3/libraryKey/signedThumbnailUrl/canEditV3/hasEditRole/isTeamTemplate）

## 四、裁决标准

1. **三入口（HTTP/multiplayer/livegraph）权限判定一致 + 全部绕过路径穷尽 → 确认无漏洞**，而不是"没找到"
2. 真实发现但无利用链（如 planPublicInfo IDOR：匿名读 tier/planRecordId/orgId 纯元数据）→ 按用户标准不报（避免浪费账号可信度）
3. 留下明确的"未测通道"清单（api.figma.com token），作为后续恢复测试的入口

## 五、可复用方法论："创造权限"六类思路

1. **身份声明**：URL 参数/协议帧里服务端可能信任的身份字段（userId/anonUserId/user-id/sessionId/token）
2. **角色声明**：客户端声明的 role/权限字段（multiplayer role）
3. **状态注入**：preload/缓存恢复机制里客户端可控的会话状态
4. **跨租户参数**：带 teamId/orgId/projectId 的视图或端点，尝试传他人 ID
5. **数据通道盲区**：预览图/缩略图/og 标签/嵌入/导出/库订阅等"旁路"通道
6. **独立权限体系**：同一产品的不同认证体系（REST API token vs web cookie vs WS），权限模型可能不一致

> 经验学习5/6 的高频模式与闭环标准照常适用；本案例的增量价值在于"穷尽清单"和"cookie 归属验证"两条硬规矩。

## 六、custom tools 独立权限体系（今日新攻击面，2026-08-07）

### 6.1 背景

三入口穷尽后仍无绕过，转向"独立权限体系"第六条思路：Custom Tools（AI 工具生态）有独立的 REST API（/api/custom_tools/*、/file/*/custom_tool_artifacts/*）与 livegraph 视图，权限模型可能与文件主体不同。

### 6.2 视图定位（JS 1037 chunk）

视图注册表形式：`FileCustomToolsMetadataView:()=>VT, OwnedCustomToolsView:()=>Yx`——注册名与变量分离，定义在变量赋值处：

- **FileCustomToolsMetadataView（VT）**：args=[fileKey(string), toolIds(list of uuid)]；字段 file.fileV2._validatedCustomToolRefs（args=[userId(bigint,nullable), toolIds]，expectedMaxCount=100）；resolver=HTTP sinatra_resolver/file_custom_tool_ids（queryParams: userId←上下文函数 dZ、file_key←$t("key")、tool_ids←dc("toolIds")）
- **OwnedCustomToolsView（Yx）**：args=[]；字段 currentUser.customToolsOwnedByMe（id/name/description/type/planId/latestVersion/publishedCustomTool）

### 6.3 测试矩阵（viewHash 可任意 32-hex）

| 会话 | 视图 | 目标 | 结果 |
|---|---|---|---|
| B | OwnedCustomToolsView | 自己 | 空壳（B 无工具） |
| B | FileCustomToolsMetadataView | 私有 5Gs4PaTz | 空壳（权限门在计算器层，resolver 不触发） |
| B | FileCustomToolsMetadataView | 公开 bv2nMIdF | File 对象返回 + FileCustomToolRef 查询触发 |
| 匿名 | FileCustomToolsMetadataView | 私有 | 空壳 |

### 6.4 __requestId 机制（关键突破）

1. 首次订阅公开文件：resolver 报错 `sinatraResolverError: Static queries without __requestId set`
2. JS 机制：`viewHasStaticQueries(viewName)` 为 true 时客户端 subscribe 自动注入 `__requestId`（随机 UUID）
3. 注入任意 UUID 后：resolver 经 `internal-proxy.prod.figma.com/api/internal/livegraph/sinatra_resolver/file_custom_tool_ids` 内部转发被调用——**直连该端点 403，livegraph 转发后变 401（{"error":true,"status":401,"message":""}）**，说明转发通道绕开了"内部端点直连拦截"，但还有参数/上下文缺失
4. 试图注入 userId 到 args → `viewSubscriptionFailed: 'userId' is not a valid argument`（args 校验严格，userId 只能来自上下文函数 dZ，定义在模块 599200 未下载的 chunk）

### 6.5 明天恢复点

1. 401 根因：dZ 上下文 userId 取自谁（登录用户还是文件所有者）——决定是否存在"B 查 A 私有文件工具引用"的 IDOR；__requestId 是否需要 HTTP 预注册缓存
2. 获取真实 tool_id（B 无工具；可从 Figma 社区公开 gen_tool 或 publishedCustomTool 数据找 UUID）推进 refs 校验链
3. 下载模块 599200 所在 chunk，确认 dZ/$t/dc 取值语义
4. REST 侧未完成对照：custom_tool_artifacts/batch（私有 403 vs 公开 422 已确认权限门存在）、GET /api/custom_tools/artifacts/{toolId}/versions/{version}（编码崩溃中断，需 text=False/errors=replace 重跑）
