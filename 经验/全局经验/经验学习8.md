# Git 密钥泄露推送拦截与历史清理

> 定位：执行规范。处理 GitHub Push Protection（GH013）拦截含密钥推送的完整流程：定位、重写历史、清理残留、防复发、验证、重推。

## 一、问题现象

`git push` 被远程拒绝，报：

```
remote: error: GH013: Repository rule violations found for refs/heads/dev.
remote: - PUSH PROTECTION - Push cannot contain secrets
remote:   —— Amazon AWS Access Key ID ———— locations: commit: <hash> path: xxx:123
```

要点：拦截是**整个推送级**的，报的是推送中任一提交内的密钥；只报第一个命中的位置，实际波及可能更广。

## 二、核心认知（先想清楚再动手）

1. **GitHub 扫描的是推送中的所有提交（含历史）**。只改工作区文件、再提交一个新 commit 无法解决问题，旧提交里的密钥仍会被拦截。必须重写历史。
2. **抓包/页面快照类文件不应入库**：HTML 快照的 `INITIAL_OPTIONS` JSON、WebSocket 流量 JSON 等常内嵌第三方明文凭据（AWS Access Key + Secret 成对出现）和 SigV4 预签名 URL（`X-Amz-Credential=AKIA...`）。预签名 URL 里的 Key ID 与明文 Secret 组合会被 secret scanning 识别为真实凭据。
3. **密钥可能是第三方的**（抓包自目标站点，如 Figma 页面内嵌的 AWS 配置）：清理目标是让仓库不再携带该凭据，不需要也不应轮换任何自己的凭据。
4. origin 上若没有这些含密钥的提交，重写历史后**普通 push 即可，无需 force push**。

## 三、处理流程

### 1. 全历史定位波及范围

拦截只报第一个文件，必须扫描所有提交确认全部波及点：

```bash
git log --all --format='%H' | sort -u | while read c; do
  git grep -lE 'AKIA[0-9A-Z]{16}' "$c" -- . 2>/dev/null | sed "s|^|$c |"
done | sort -u
```

同时扫描其他常见密钥模式（`figd_`、`ghp_`、`github_pat_`、`xox`、`AIza`、`sk-`），排除 JS chunk 中的误报（已成功推送的提交里就有，可用来对比哪些模式不会被拦截）。

### 2. 备份工作区文件

filter-branch 重写后**会连带删除工作区中从历史移除的文件**，先备份：

```bash
mkdir -p /tmp/scan_backup
cp <file1> <file2> /tmp/scan_backup/
```

### 3. 重写历史，移除含密钥文件

```bash
git filter-branch --force --index-filter \
  'git rm --cached --ignore-unmatch _figma_hunt/editor_page.html _figma_hunt/ws_traffic.json' \
  --prune-empty <坏提交>^..dev
```

- `--index-filter` 只操作索引，比 tree-filter 快（不 checkout 每个提交）。
- 只从引入密钥的提交开始重写，不动更早的历史。
- 若文件是要保留的分析材料，也可改用 tree-filter 把密钥替换为占位符；但抓包快照建议直接移除。

### 4. 删除 filter-branch 备份引用

filter-branch 会在 `refs/original/` 留下旧 ref，导致 `git log --all` 和密钥扫描**仍命中旧提交**：

```bash
git update-ref -d refs/original/refs/heads/dev
```

### 5. 防复发：更新 .gitignore

```bash
# 抓包快照（含预签名凭据，不入库）
_figma_hunt/editor_page.html
_figma_hunt/ws_traffic.json
```

### 6. 恢复工作区文件

```bash
cp /tmp/scan_backup/<file1> /tmp/scan_backup/<file2> <原目录>/
```

### 7. 验证（三步缺一不可）

```bash
# ① dev 全历史无密钥模式
git log dev --format='%H' | sort -u | while read c; do
  git grep -lE 'AKIA[0-9A-Z]{16}' "$c" -- . 2>/dev/null
done
# ② 无 original 残留
git for-each-ref | grep -i original
# ③ 与 origin 差异正常（领先数符合预期，工作区干净）
git rev-list --count origin/dev..dev
git status --short
```

### 8. 重新推送

```bash
git push origin dev
```

## 四、必要条件与失效条件

- 必要条件：含密钥的提交尚未推送到 origin（或用户接受 force push 改写远程历史）；确认密钥为第三方或已作废，无需轮换。
- 失效条件：密钥同时存在于已推送的历史中（需 force push，且 GitHub 对已公开泄露的密钥仍会继续告警）；多个密钥分散在多个文件（漏扫即再次被拦截）。

## 五、常见坑

- 只清理 GitHub 报告的单个文件，漏掉同批其他文件（本次 `ws_traffic.json` 的预签名 URL 带同一 Key ID）。
- 忘记删 `refs/original/`，验证时误以为清理失败。
- 忘记备份工作区文件，filter-branch 后材料丢失。
- 把含密钥文件重新 `git add -A` 入库（.gitignore 必须同时更新）。

## 六、证据标准

- 重写后扫描 dev 全部提交无目标密钥模式。
- `git status` 干净、`.gitignore` 含被删路径、无 original ref。
- push 成功且 `origin/dev..dev` 为 0。

## 一句话总结

推送被密钥拦截时，唯一解法是重写未推送的历史：先全历史定位、备份工作区、filter-branch 移除、删 original ref、加 gitignore、恢复文件、验证三步、再推；抓包快照类文件从一开始就不该入库。
