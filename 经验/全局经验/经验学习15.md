# 经验学习15：多账号 Cookie 污染假阳性判定与身份声明类漏洞终极验证(Figma 实战 2026-08-19)

- 定位:方法 / 执行规范 + 案例
- 来源:Figma 旧 H1 报告(H1-identity-claim-authz-bypass)被纯净 cookie 矩阵推翻全复盘
- 性质:可复用方法论(不局限于 Figma),已收束结论供后续直接引用

## 一、案例:一份 HIGH 报告的推翻过程

**旧报告主张**:`/api/file_metadata` 和 `/api/ai_chat/*` 信任 `X-Figma-User-ID` 头 / `fuid` 参数声明的身份,不校验 cookie。证据:B cookie + 随机 uid → 200 泄露 owner uid/realtime_token;B cookie + fuid=A → 200 读到 A 的全部 AI 线程和对话。

**推翻证据(2026-08-19 六组对照矩阵)**:

| 请求 | 纯净 B cookie | 原始 B cookie(含 A+B token) |
|---|---|---|
| threads + fuid=随机 | 403 | 403 |
| threads + fuid=A | 403 | 200 泄露 A 线程列表 |
| threads + header=A | 401(mac 校验) | 200 |
| file_metadata + header=随机 | 403 | 200 泄露 realtime_token |
| owner 基线(纯净 A + header/fuid=A) | 200 | — |

**结论**:fuid/header 声明的身份必须存在于 cookie token 集合,否则 403/401。"随机 uid 也 200"是服务端对无效声明的**回退行为**,不是信任行为。

## 二、核心机制:无效身份声明的三种服务端行为(假阳性根源)

攻击者声明一个身份,服务端可能:

1. **拒绝**(理想):声明不在 cookie token 集合 → 403/401(纯净 B 全组合都是这个结果)
2. **回退**(多账号陷阱):声明无效 → 忽略声明,用 cookie 中**任意有效 token** 处理 → 若抓包 cookie 恰含目标账号 token → 200 泄露 → **假阳性**
3. **信任**(真漏洞):声明谁就是谁 → 任意登录用户伪装任意用户

**判定口诀**:看到一个"身份声明越权"候选漏洞,第一反应不是兴奋,而是问:**我的 cookie 里有没有对方的 token?** 多账号浏览器抓包几乎必然中招(本案例 B 浏览器同时登录 A+B,`authn` 和 `embed` 两个字段都含双 token)。

## 三、验证方法论:绝对纯净 Cookie 对照矩阵

1. **解析 cookie 身份字段**:`__Host-figma.authn` 是 URL 编码 JSON,key=uid,value=token;`__Host-figma.embed` 同样结构,**是第二身份载体**(曾导致 FileByKey 假阳性)
2. **构造绝对纯净 cookie**:authn+embed 都只留攻击者自己的 uid token(紧凑 JSON 重新 URL encode);embed 清空后连 `embed.mac` 一起删
3. **对照矩阵**:纯净 vs 原始 cookie × (fuid 参数 / X-Figma-User-ID 头) × (随机 uid / 目标 uid),再加 owner 基线(纯净 A 自己访问 → 200 证明构造有效)
4. **判定**:纯净 + 伪装身份 = 403/401/空壳 → 绑定存在,非漏洞;纯净 + 伪装身份 = 200 且真实数据 → 漏洞坐实

## 四、附带验证的已有结论(直接引用)

- `messages` 端点对不属于该文件的线程返回 404 "Thread not found" = 线程按 owner 命名空间隔离(查询层隔离,强绑定)
- 纯净 cookie 下 header 伪造 → 401 空 message(mac/绑定校验);fuid 伪造 → 403 "no permission to use AI in this file"(文件权限层拒绝)
- 修改 authn 后 `__Host-figma.authn.mac` 不匹配 → 401,说明部分接口校验 mac
- 报告关闭处理:提交后发现问题第一时间撤回/关闭并说明原因,保护账号可信度 > 保留一个注定 Informative 的报告
