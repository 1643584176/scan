# 高频漏洞模式补充

> 定位：模式目录。用于提出假设，不作为“发现即成漏洞”的判断依据。

额外值得 AI 学习的漏洞思维 & 漏洞模式（依然重思路，不背 payload）
承接上面整套猎人思考框架，补充现实 HackerOne 高频、但前面没覆盖的模式，分为：逻辑漏洞、解析 / 协议层缺陷、业务状态机、密码与会话、反序列化、条件竞争、绕过防护、漏洞评估思维、假阳性排查、报告思维。
全部输出思考提问清单，给 AI 做推理模板，不是复制 exp。
一、业务状态机 / 业务逻辑漏洞（HackerOne 大量高分漏洞，容易被扫描器漏掉）
扫描器几乎扫不出来，靠人对业务流程理解。
核心：业务有一套状态流转规则，攻击者干涉状态跳转，跳过业务约束。
思考提问清单：
完整业务流程是什么？允许的状态顺序是什么？
是否可以直接调用后端接口，跳过中间业务步骤？
是否允许重复执行本应该只能执行一次的动作？
状态变更时，后端是否校验前置状态是否合法？
多步骤业务：付款‑下单‑退款‑提现，每一步后端是否独立校验，还是信任前端传过来的状态？
是否存在状态篡改：把未支付改为已支付、取消订单改为有效订单。
金额、数量类参数：能否传入负数、0、超大值，造成业务异常。
典型例子：越权退款、重复提现、免费购买商品。
AI 要学会：梳理业务允许的状态图，尝试打破状态流转顺序。
二、条件竞争（Race Condition / TOCTOU）
时间窗口类漏洞，检查和使用不是原子操作。
思考提问清单：
是否存在：先做一次权限 / 状态检查，之后再执行操作，中间存在时间间隙？
检查和修改是不是同一个原子事务？
是否可以并发并行发送多个请求，在检查之后、生效之前篡改资源条件？
资源删除、余额扣减、角色变更场景，是否有防并发机制（锁、数据库事务）？
认知：
很多漏洞不是单请求复现，需要并发请求；单条请求看不出问题。
AI 不能只分析单次请求，要思考：并发同时调用会发生什么。
三、解析器歧义、协议解析绕过（Parser Confusion）
HTTP、JSON、multipart、表单解析差异，不同组件解析理解不一致，造成绕过。
本质：A 组件解析得到 A 语义，下游 B 组件解析得到 B 语义，利用解析差异绕过校验。
思考提问清单：
多个组件依次处理同一个输入：Nginx → Web 框架 → 应用代码，各个组件对特殊字符解析是否有差异？
Content‑Type、边界符号、换行、空字节、特殊空白字符会不会改变解析结果？
multipart 表单：文件名字段、字段名，是否会被解析器特殊处理？
JSON/HTTP 参数混淆：同时传 JSON body + url query 参数，框架优先取哪一个？是否出现参数污染（HTTP Parameter Pollution）。
过滤只在第一层解析生效，下游解析会重新解释转义字符。
例子：HTTP 参数污染、空字节截断、multipart 文件名绕过、json 与 form 参数覆盖。
AI 思考重点：同一输入流经多个解析器，各个组件理解是否不一致。
四、反序列化类思维（PHP / Java / Node.js）
不背 gadget 链，学习怀疑点。
思考提问清单：
是否接收原始序列化字符串来自外部用户可控输入？cookie、http body、参数。
反序列化之前有没有做完整性校验（签名、hmac）？
业务是否信任反序列化出来的对象属性？攻击者是否可以控制对象内部属性。
即使不能直接 RCE：反序列化是否可以修改业务对象属性，实现业务绕过？
认知：
反序列化不一定直接 RCE；很多时候只是对象属性篡改，实现权限绕过。
五、会话、认证、JWT 类思考
思考提问清单：
JWT：签名、算法、issuer、audience、时效与密钥轮换是否被完整校验；旧式 `none`/算法混淆仅在具体库或错误配置确有接受行为时成立，不应机械尝试或默认存在。
JWT payload 全部可控，后端是否只依赖 payload 里面字段，不在服务端重新查询数据库真实权限？
重点误区：不要相信 JWT 里面存储的角色，后端要查数据库。
Session：会话 ID 是否做失效处理；改密码、登出之后旧 session 是否依然有效？
是否允许会话固定：攻击者可以设置受害者 session id。
密码重置逻辑：重置 token 是否足够熵；是否可暴力；是否可被篡改绑定到其他账号。
AI 关键点：不要信任客户端携带的身份数据，关键信息后端必须查询数据源校验。
六、防护机制本身的绕过思维（WAF、RBAC、黑名单、速率限制）
不是直接找绕过 payload，思考防护逻辑缺陷。
思考提问清单：
防护逻辑在哪个组件执行：反向代理？应用层？
防护是黑名单还是白名单；黑名单是否只检查特定位置？
是否可以通过编码、拆分请求、分片，把恶意字符放到过滤器看不到的地方？
Rate‑limit 限流：是针对 IP，还是用户账号；是否可被多账号、多 IP 绕过。
RBAC 权限系统：是在每个接口做校验，还是靠中间件；是否存在接口跳过中间件。
文件上传防护：校验文件内容还是仅校验文件名后缀；校验在前端还是后端。
核心：看 “防护生效的位置”，攻击者能不能把恶意数据送到防护逻辑没有覆盖到的代码路径。
七、间接风险 / 二阶漏洞（Stored / Second‑order vulnerability）
输入点和触发点不在同一个请求。
输入请求 A 提交恶意载荷，当时没有异常；
在后续另一个请求 B，载荷才被执行 / 触发危害。
思考提问清单：
用户可控数据存入数据库；不在 A 请求触发，在别的页面、别的功能读取渲染才触发。
漏洞现象不在提交的接口响应体现，需要访问另外一个页面才复现。
报告时容易漏掉：测试接口看返回一切正常，认为没问题。
例子：二阶 SQL 注入，存储 XSS。
AI 要学会：跟踪数据存入存储之后，后续所有读取这条数据的代码路径。
八、漏洞评估思维（非常关键：区分严重程度，判断值不值得报 HackerOne）
教会 AI 不要发现一个异常就判定高危，学会评估真实现实影响。
评估思考维度清单：
前置条件集合：需要什么权限？需要用户交互？需要特殊环境？
攻击门槛：是否需要高难度并发、特殊内网环境、很难构造的条件。
影响范围：影响单个用户、一批用户、全部系统、服务器。
现实缓解：是否默认有 WAF、IP 白名单、SameSite、CSP 等现实缓解条件。
可复现稳定性：稳定复现，还是极难复现的边缘情况。
有没有安全边界补偿机制，降低实际风险。
很多实验室环境可以复现，真实线上有多重缓解，只能算中低危。
九、识别假阳性的补充清单（减少 AI 乱报漏洞）
出现下面情况，高度怀疑是假阳性：
攻击载荷执行必须修改服务端本地配置，默认环境不具备。
只能造成服务端崩溃 DoS，但是厂商有保护、自动重启，无数据泄露 / 篡改。
只能在报错页看到一些元信息，无法进一步利用。
利用必须攻击者拥有管理员本身权限。
所有利用条件全部在攻击者客户端，不能影响服务端与其他用户。
十、漏洞报告思维（AI 输出报告的思考方式）
先写复现前置条件，再写复现步骤；不要上来直接写 payload。
区分：观察现象、推测根因、实际业务影响。
写清楚：什么角色账号，哪些 http 请求，业务发生了什么变化。
分层修复：紧急缓解、代码层修复、架构层面改进。
写明缓解条件：什么配置会让漏洞无法利用。
十一、需要新增植入 AI 的认知补充
漏洞不一定发生在输入点；很多漏洞发生在数据被取出使用的地方（二阶漏洞）。
很多高危漏洞不靠注入、RCE；业务逻辑、状态机、条件竞争同样高分。
不同组件解析不一致是一类巨大攻击面。
JWT、Session 不要信任客户端携带的身份信息，服务端数据库才是真相源。
防护在哪里执行，比防护写得有多复杂更重要。
评估漏洞要结合线上实际环境，不要只看裸测试环境结果。
