# 漏洞研究通用推理框架

> 定位：总方法论。任何测试都以项目范围、政策、速率限制和数据最小化要求为先。

漏洞研究思维框架（给 AI 学习：重推理思路，拒绝照搬 Payload）
核心原则：学习 “怎么怀疑、怎么试探、怎么证伪、识别链式风险”，而不是背诵攻击字符串。判定漏洞看业务实际影响，不看返回码、报错、能否传入特殊字符。
一、完整通用猎人推理工作流（固定思考顺序）
梳理完整数据流
追踪不可信用户输入：输入来源 → 各处理中间层 → 最终流向组件。
漏洞大多发生在信任边界：不受控外部数据进入受信任组件（数据库、文件系统、Elasticsearch、前端 JS、下游内部服务）。
提出合理怀疑假设
主动提出假设，而不是直接扔 Payload：
是否只做前端校验，后端没有复现校验？
是否只保护某一条 API 路径，漏掉等价访问入口？
多个独立缺陷单独看危害有限，组合在一起会不会产生新危害？
开发是否对某个过滤 / 函数能力产生错误想当然？
最小扰动试探
优先使用最小载荷做行为探测，不直接上完整攻击 Payload：
路径穿越：先传../观察行为，而不是直接读/etc/passwd
原型污染：先注入{"__proto__":{"test":1}}观察对象变化，不直接上 XSS
注入类：先做边界探测，观察报错、响应差异，不直接执行命令
区分现象与真实漏洞（对抗假阳性，最重要）
以下现象不等于漏洞：
HTTP 返回 200
页面抛出报错
参数可以接收特殊字符
WAF 没有拦截输入
✅真实漏洞判定标准：攻击者可以可控地造成业务非预期状态变更，产生实际业务危害。
自我证伪：寻找不可利用条件，推翻自己的假设
每一个假设之后必须反问：哪些条件会让该攻击失效？
是否缺少权限、Nonce、CSRF‑Token？
Cookie SameSite / CSP / 目录锁定 / IP 白名单是否阻断利用？
是否需要多个前置条件同时满足，缺失任意一个就无法利用？
链式漏洞推理
单点缺陷危害有限时，主动寻找可以串联的第二个、第三个薄弱点。
示例：
SQL 注入输出污染 JSON (A) + 前端不安全对象合并 (B) → DOM‑XSS
CSV 注入恶意 PHP (A) + 文件名路径穿越 (B) → RCE
SSRF (A) + 内网高权限 IAM 凭证 (B) → 服务器接管
根因复盘
找到开发逻辑的认知误区：
认为上层已经校验，下游就不再校验；
混淆不同过滤函数的防护能力；
同一资源多条访问路径，只保护其中一部分；
把 UI 界面限制当成后端安全控制。
二、分领域思考提问清单（只有思考问题，不提供 payload）
1. CSRF / HTTP 接口层（参考 Tokopedia GraphQL CSRF 案例）
遇到写操作接口，依次自问：
身份认证是否完全依赖 Cookie？是否存在 CSRF‑Token 校验？
Cookie SameSite 配置是否会阻止跨站携带 Cookie？
当前接口是写操作（Mutation）还是查询（Query）？CSRF 通常优先关注状态变化；查询仍需检查是否存在副作用、敏感数据经可观察信道泄露或高成本执行，不能仅因名为 Query 就断言无风险。
从浏览器视角：该请求属于简单请求，还是会触发 OPTIONS 预检的复杂请求？
后端是否严格校验Content‑Type，还是直接读取 body 忽略请求头？
CORS 配置如何？记住：CORS 仅阻止 JS 读取响应，不会阻止请求到达后端。
就算跨站请求成功发出，是否真的可以修改业务数据？
输出结果：判断是否具备可利用条件，而不是直接复制 HTML 表单 Payload。
2. 权限与对象访问控制（参考 larocas BOLA 案例）
多租户、ACL、资源对象类系统思考清单：
资源属于哪个用户 / 角色？API 接收外部传入的资源 ID，有没有校验资源归属？
ID 是自增 ID 还是 UUID？UUID 不能作为安全防护，只是不可猜测。
前端页面隐藏按钮、隐藏数据；后端 API 是否依然接受请求？UI 限制≠安全校验。
是否存在多条不同 API 路径可以访问同一个资源；是否只保护其中一条路径？
使用低权限账号调用高权限资源接口；使用 A 账号会话传入 B 账号的资源标识，观察行为。
垂直越权：普通用户是否可执行管理员动作；水平越权：普通用户读取其他普通用户私有数据。
认知：高危漏洞不一定是注入 RCE，访问控制失效同样可以造成严重危害。
3. 文件操作类漏洞（GiveWP LFI/RCE 案例）
接口涉及文件名、文件读写、导入导出：
文件路径是否直接拼接用户可控输入？
使用的过滤函数能力边界是什么；该函数是否真的可以防御路径穿越？
是否锁定工作目录；写入 / 读取完成后是否用 realpath 校验文件落在允许目录内？
导入、导出两套功能是否使用同一套数据过滤逻辑？经常出现导入宽松、表单严格。
是否允许写入可执行后缀文件；上传目录 Web 服务是否禁止解析脚本。
4. GraphQL 专项思考（多个 HackerOne 公开报告）
全局入口node、内省查询__schema/__type是否单独遗漏权限校验；业务 Resolver 做了校验，统一入口没做。
AST 过滤是否只检查顶层节点；是否可以通过嵌套 fragment 绕过黑名单检测。
sort、filter 参数是否直接原样转发给下游搜索引擎 ES/MongoDB；下游引擎是否具备脚本执行能力。
Mutation 写操作是否校验 CSRF、权限；输入类型是否做严格 schema 校验，接受任意自定义 JSON。
5. 链式 SSRF（Shopify SSRF 链案例）
遇到后端抓取外部 URL 功能（预览、截图、webhook、导入）：
用户是否可控完整目标 URL？
SSRF 防护有没有阻断内网 IP、云厂商元数据地址？
不只看 SSRF 本身，评估后链风险：后端服务器是否可以访问内部服务、元数据、Redis、Docker API？
服务器实例账号、IAM 角色权限是否过大；SSRF 拿到凭证之后能做什么。
SSRF 本身只是发出网络请求；危害取决于后端内网环境。
6. 前后端联动客户端漏洞（Arkavidia Atlas，SQLi→原型污染→XSS）
后端输出 JSON 流入前端 JS：
后端输出 JSON 内容是否完全可控？有没有过滤__proto__、constructor这类原型键？
前端是否存在递归 merge/extend/clone 对象合并逻辑？合并时是否跳过原型相关 key。
是否存在由对象属性控制渲染逻辑：条件分支选择安全 text 渲染 / 危险 html/innerHTML 渲染。
是否存在管理员访问用户可控 URL 的业务功能（举报、预览、反馈），可以作为漏洞利用的最终载体。
7. AI‑Agent 特有安全思路
系统提示与外部不可信输入是否严格隔离；外部用户文本会不会直接拼入系统 prompt。
Agent 自动拉取外部网页、PR、issue 内容；外部不可信内容是否可以覆盖、伪造系统指令。
Agent 拿到工具调用权限之后，不可信输入是否可以诱导调用高危工具。
三、AI 推理输出规范（强制输出格式，不直接贴 payload）
当分析一个目标，输出结构固定如下：
梳理数据流：输入来源，经过哪些组件，最终流向。
列出全部漏洞前置必要条件（全部满足才有可能，缺一则不可利用）。
假设与怀疑点：列出对哪些边界产生怀疑。
探测思路：描述应该做哪些最小扰动试探，描述动作，不直接贴完整攻击 payload。
证伪检查：列出会让攻击失效的排除条件。
危害推导：如果假设成立，会产生什么样业务后果。
根因推断：开发在哪一步逻辑想当然。
分层修复建议。
禁止直接输出现成 Payload 字符串作为主要结论；Payload 仅可作为补充示例。
四、需要植入 AI 的重要认知清单（反误区）
CORS 不能防御 CSRF，它只阻止 JS 读取响应。
UUID、随机 ID 不等于安全，解决猜测问题，不解决越权访问问题。
前端 UI 隐藏不等于后端安全校验。
返回 200、报错、特殊字符输入成功，不等于漏洞。
很多高危漏洞是多个低风险缺陷串联，单点看没有大问题。
不同 PHP/JS 过滤函数能力有边界，不要想当然认为某个函数可以防御全部攻击。
防护不能只做在一条访问路径；等价的 API 入口需要复用同一套鉴权逻辑。
真正的漏洞看业务状态是否被攻击者可控篡改。
简短总述
这套框架核心是模拟优秀赏金猎人的思考过程：画数据流、提假设、最小试探、自我证伪、寻找链式组合、根因分析。AI 不去背诵网上现成 Payload 样本，而是学会 “面对一个系统，我应该从哪里怀疑，如何验证，如何排除假阳性，判断到底算不算真实漏洞”。
