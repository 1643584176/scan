- 性质：**强制学习、强制执行**——不是参考思路，是审查接口时的默认神经回路
- 复核日期：2026-08-17

## 适用范围

所有 Web/API 目标（Figma、Shopify、Superhuman 等）。不区分漏洞类型，适用于任何接口审查、请求构造、结果解读。

## 一、信念层（分析 H1 报告的根本目的）

1. **每个网站都有漏洞，只是我们没发现**：H1 上每个大目标都有已披露的真实漏洞，没有任何网站是无洞的；已披露的只是冰山一角。连续测试全被封死时，结论不是"这网站安全"，而是"我还没找到角度"。

## 二、筛选层（什么才算漏洞）

2. **注入三元组 = 真正意义上的漏洞**：注入**什么**（载体：参数/请求体字段/header/cookie/文件名/URL/模板字段/JSON键名）→ 注入到**什么地方**（消费点：SQL查询/命令执行/模板引擎/文件路径拼接/HTTP请求构造SSRF/日志/响应头/正则/反序列化）→ 导致**什么问题**（后果：数据泄露篡改/RCE/SSRF/任意文件读写/响应头注入/日志伪造）。权限/逻辑类是"判断遗漏"（加个 if 就修好、影响单点）；注入类是"信任了不该信任的输入"（影响执行层/数据层，修复要重构），才是高危。**判定标准：发现必须能写成完整三元组，写不出的都是小儿科，不值得报告。**
3. **公开性检查（提交前必做）**：判断查到的东西是否公开——公开的发现毫无意义（by design/必 dup/对面早知道）。检查五问：① 该数据是否无需任何凭据即可获取（匿名直连/公开页面/公开 API）？② 目标对象本身是否被 owner 设为公开（公开分享/公开文件）？③ 其他用户/匿名用户是否本就有权查看（有 = 不是漏洞）？④ 数据是否出现在产品页/营销页/文档等设计公开渠道？⑤ 获取路径是否需要特殊知识（deep link/未公开参数）——若公开渠道同样能拿到，特殊路径也不构成泄露。任一为"公开"→无意义，不报告。PlanByFileKey 匿名计费数据被关 Informative 的教训：提交前未做公开性检查。
4. **不做没有参考意义的东西**：禁止枚举接口（拿清单逐个打）、禁止枚举 ID（猜值/遍历）、禁止无确定性来源的探测。每个动作必须同时满足：① 确定性来源（JS 调用定义/真实抓包/已有日志证据）；② 预定义目标结果（能写成三元组或业务状态变更）。缺任一即不做，立即切换方向。

## 三、判断层（解读响应与校验）

4. **403 是指纹不是终点**：每个 403 都是一段校验逻辑存在的证据。问：判断由什么构成？缺什么会导致放行？判断构成三问——校验对象是谁（身份/归属/属性）、校验依据来自哪（header/cookie/参数/查库）、什么输入不经过这个判断（其他入口/其他表示/其他客户端）。逐项消除法：每次只撤一个条件重试，看哪个被撤后放行。
5. **200 不等于无问题**：只证明该请求组合被接受。追问未消费的入参（隐形字段）、未测的状态组合（已删/已撤销/已移除后旧引用）、未试的表示形式。
6. **"参数恰好传对"是测试盲区**：网站看起来没漏洞，可能只是参数传对了（自己的 ID/正确格式/完整必填）。"传对了"本身证明服务端在消费该参数做判断——逐个参数变形（换值/删/改格式/改表示）重试，看同一判断是否被一致执行。注意多参数联合校验（A+B 只改 A 保留 B，判断不破）和三层"对"（值对/格式对/表示对）。
7. **越权越没有问题，洞在判断不一致处**：越权是所有人第一个测的，成熟网站防护最严，直接换 ID 读他人数据几乎不存在。"越权被防住"不是结论而是证据——归属判断存在；真正的洞在判断的不一致处（同数据多入口权限不一致、新功能子系统分支没继承校验、状态转换后旧权限残留），不在判断缺失处。
8. **身份从 cookie 来，别把对面当傻子**：后台取身份从会话 cookie 取，不从请求参数取——传谁的 ID 都没用，基础越权（A 访问 B）必然被拒。权限问题是所有测试者都知道的核心，对面工程师更知道，基础权限校验（身份→归属→授权）一定存在且严密，不要在"校验是否存在"层面浪费时间。真正的测试面：URL 即凭证的资源（预签名/一次性token/匿名通道——鉴权依赖 token 本身，测 token 生成/可预测性/生命周期）、新对象/新子系统的归属模型（AI 沙箱/snapshot 等派生对象——校验可能在创建时做了，但对象与源资源的权限关系是新逻辑，问"判断有没有继承"）、从 cookie 取值的业务字段（cookie 存了 fileKey/teamId/角色等可控字段，篡改看判断是否被绕过）。

## 四、战场层（漏洞在哪）

9. **漏洞集中在处理逻辑层，不在权限层**：权限判断是"明牌"（人人知道要做）；漏洞集中在接口绕过（前置检查/网关/校验层的可绕过路径：表示变换/入口变换/路径归一化/大小写编码变体）、接口返参（响应返回不该返回的字段/对象——对每个响应字段问"为什么出现在这里"）、入参/请求体/header 的处理（服务端在哪些地方消费客户端可控输入）、以及**函数问题（出漏洞概率极高）**：解析函数（JSON/URL/QueryString 对重复键/嵌套/畸形/超大值的宽容性）、编解码函数（双重解码/base64变体/URL编码差异/Unicode归一化）、类型转换（宽松比较/截断溢出/数组vs标量）、哈希签名函数（alg混淆/密钥选择错误/长度扩展/时序比较）、随机ID生成（可预测/时间戳种子/计数器/短ID）、字符串处理（截断/大小写/空字节/换行）、路径文件处理（拼接/扩展名判断/符号链接）、状态转换函数（状态机边界/重复转换/回退/撤销后重放）、聚合批量处理（首项校验/去重/排序后处理/分页游标）。触发方式：畸形输入（"参数恰好传对"的反面）。
10. **页面判断 → 参数 → 接口 映射提取**：JS 里每个接口调用周围的条件分支（什么时候调、带什么参数、什么条件下才带某参数）就是后端参数契约的确定性来源——抓包看不到（未触发条件）。对每个调用点向上追溯调用链（函数入参/状态变量/权限标志），列出"判断→附加参数"映射（isOwner→带 ownerToken、teamLibrary→加 teamId header、aiEnabled→带 aiSession、isAdmin→加 role 字段）。这些隐形参数逐一变形重试，看后端判断是否依赖。页面判断可绕过：前端不满足条件就不调用，但后端可能不校验——直连不带条件参数仍正常处理 = 该判断只存在于前端。双重用途：参数契约来源 + 前后端判断一致性对比。

## 五、竞争层（你的竞争力）

11. **竞争视角：站在前置黑客的角度审查**：你不是唯一在找漏洞的，大目标有大量赏金猎人和自动化扫描器。自然的思路（换 ID/改参数/常见绕过）别人早试过，洞早被补，提交必 dup。每个测试想法先问"前置黑客会不会也这么想"，再问"他们为什么没想到"——独特角度来自：深度 JS 逆向（别人只看抓包）、异常状态转换（别人只测正常流）、跨子系统组合（别人单测一个域）、新功能初期防护不完整、非标准表示。H1 hacktivity 已披露的同类漏洞类型 = 已被覆盖区域，避开。

## 六、学习层（测后闭环）

12. **温故而知新，测后必复盘**：测完不是结束。复盘回答：这次为什么想到这个测试点（什么证据/思路引导的）？结果证明了什么？哪个推理错了？下次遇到类似场景第一反应该是什么？提炼可迁移的推理路径（业务场景→怀疑点→验证方式），不是记录"测了什么/得到什么响应"的流水账。定期温习 H1 报告分析（_h1_toolkit/ANALYSIS.md）、历史复盘、本经验库——每次温习都要产生新的怀疑点。新思路即时沉淀到 skill/记忆/工具包，不让用户重复指导。

## 常见假阳性 / 失效条件

- "响应有差异"不等于漏洞——写不出三元组就是小儿科
- 直接换 ID 测越权 = 浪费时间且暴露意图——基础校验必然存在
- 拿接口清单逐个打 = 测项目式验证，对报告无价值（Notion 61+ 端点矩阵教训）
- 枚举参数名/ID 值 = 无确定性来源，禁止
