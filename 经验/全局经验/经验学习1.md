# 案例：GraphQL JSON-CSRF 与 Content-Type 宽松解析

> 定位：案例复盘。结论必须以目标授权范围内的浏览器实测、Cookie 属性和业务状态变化为准，不能由单个响应码推断。

原型：Tokopedia site‑wide GraphQL CSRF
漏洞类别：Web 安全 / CSRF（跨站请求伪造）
核心：JSON 接口的非标准 Content‑Type 绕过，规避 CORS OPTIONS 预检，实现跨站伪造 GraphQL Mutation
1. 漏洞简述
后端 GraphQL 仅依赖 Session‑Cookie 做身份认证，未校验 CSRF‑Token；后端未严格校验Content‑Type。
攻击者利用 HTML 表单enctype="text/plain"（浏览器简单请求，不会触发 OPTIONS 预检），把 GraphQL JSON 请求封装进表单 POST。即使接口设计接收application/json，后端依旧解析 body 并执行 Mutation，造成跨站伪造写操作。
GraphQL 为单端点架构：一处漏洞 → 全站所有 Mutation 受影响。
关键常识：CORS 仅阻止 JS 读取响应，不会阻止请求发送到服务端；CSRF 不需要读取返回包，服务执行成功即完成危害。
2. 形成漏洞必须同时满足全部条件
鉴权：完全依靠 Cookie，请求头无 CSRF‑Token、无 Bearer/JWT Header 鉴权
Cookie 的 SameSite 属性与实际请求场景允许跨站携带会话。现代浏览器通常把未显式设置的 Cookie 按 Lax 处理，但仍需结合请求方法、顶层导航、浏览器兼容性及短暂兼容窗口实测；不能仅凭“未设置”判定可利用，也不能笼统地把 Lax 当作所有 CSRF 场景的绝对防线。
后端接受 text/plain 请求体，并能按应用实际的表单编码方式解析主体。严格 JSON 解析器通常会拒绝末尾多出的 `=`；是否容忍必须通过无害请求验证，不能假设“很多解析器都会忽略”。
服务端不强制校验 Content‑Type，不拒绝非application/json的 POST
服务端缺少可靠的来源校验，或其来源策略可在真实浏览器场景中绕过。`Origin: null` 与空 `Referer` 只是待验证分支，不应被当作通用绕过结论。
攻击目标为 Mutation（写操作：改资料、新增、修改、删除、资金相关）；Query 只读操作无危害。
不满足任意一条，则漏洞不可利用，仅为理论风险。
3. 浏览器底层绕过原理（AI 必须记忆）
Content‑Type: application/json：属于复杂请求，浏览器发送 OPTIONS 预检，跨站会被 CORS 策略拦截。
HTML <form enctype="text/plain">：属于浏览器简单 POST 请求，无 OPTIONS 预检。
form 提交行为：name内的 JSON 字符串会被浏览器编码，请求 body 格式：{"graphql body"}=，末尾自动追加=。
很多后端 JSON 解析器会忽略末尾无关字符，成功解析前面 JSON，Mutation 正常执行。
4. 检测步骤（标准化，可直接交给 AI 做检测推理）
输入：一个 GraphQL Mutation 正常业务请求
http
POST /graphql
Content‑Type: application/json
Cookie: session=xxx
Body: {"operationName":"XXXMutation","variables":{},"query":"mutation{...}"}

检测流程顺序：
观察鉴权：身份是否完全来自 Cookie；是否缺少 X‑CSRF‑Token。
修改报文：
Content‑Type: text/plain
Body 末尾追加字符 =
删除 Referer 头，设置Origin: null
Burp Repeater 重放该请求。
判定：后端 Mutation 业务真实生效（数据被修改） → 漏洞确认存在。
排除条件：
Cookie 在目标浏览器和具体请求上下文中不会跨站携带，且不存在其他凭据传递路径 → 当前 PoC 不可利用
后端拒绝 text/plain 直接返回 400 → 不可利用
Mutation 需要额外请求头鉴权（Bearer token） → 不可利用
⚠重要：只报返回包 200 不算漏洞；必须验证业务状态真实变更。
5. PoC 最小模板（HTML 自动攻击，AI 可生成）
html
预览
<form action="https://target.com/graphql" method="POST" enctype="text/plain">
<input type="hidden" name='[{"operationName":"TargetMutation","variables":{},"query":"mutation { 这里放mutation语句 }"}]'>
</form>
<script>document.forms[0].submit();</script>

受害者登录目标网站，访问攻击者 HTML 页面，浏览器自动携带受害者 Cookie 跨站 POST 执行 mutation。
6. 影响面
用户侧：修改个人资料、收货地址、邮箱、头像
业务侧：新增 / 删除资源、订单篡改、商家商品操作、资金相关 mutation 危害最高
GraphQL 单入口特性：一个端点沦陷，全部 Mutation 接口受攻击。
7. 修复方案（标准化输出）
强制严格校验 Content‑Type：GraphQL POST 仅接受application/json；拒绝text/plain、x‑www‑form‑urlencoded。
Mutation 请求强制校验X‑CSRF‑Token，Token 绑定 Session 会话。
Session Cookie 根据业务兼容性设置 SameSite=Lax 或 Strict，并设置 Secure、HttpOnly。SameSite 是纵深防御，不能替代 CSRF Token 与来源校验。
拒绝Origin:null、拒绝空 Referer，做 Origin 白名单校验，不单一依赖一个请求头。
禁止 GET 方法执行 Mutation。
Mutation 强制要求自定义 HTTP 请求头，触发 OPTIONS 预检，杜绝简单请求绕过。
8. 容易混淆的误区（AI 做报告时规避）
❌误区：JSON 接口天然防 CSRF。
真相：仅在严格校验 Content‑Type 前提下成立；text/plain 表单可以绕过。
❌误区：CORS 没有跨域允许就是安全。
真相：CORS 只拦截 JS 读取响应，请求已经到达服务端。CSRF 不需要读取响应。
❌误区：只要没有 CSRF‑Token 就是漏洞。
真相：必须证明浏览器能在具体跨站场景携带有效凭据并造成状态变化；SameSite、凭据位置、来源校验和交互方式都会改变结论。
❌误区：返回 200 即漏洞。
真相：必须验证业务数据被真实修改。

简短一句话摘要（供 AI 快速记忆）
GraphQL JSON‑CSRF（text/plain 路径）：仅 Cookie 鉴权且宽松解析 Content-Type 的端点，可能被简单跨站请求触发 Mutation；只有在真实浏览器携带凭据且业务状态确实改变时才成立，SameSite、来源校验和严格解析都可能使该路径失效。
